# Quest Sorceress — Data Model

Derived from `SPEC.md` section 3. This is deliberately **platform-neutral** — the same
five entities apply whether the backend is Supabase (Postgres) or Base44.

Per the spec-first build order, this comes first because it is the most expensive thing
to change later.

---

## Entities

### User

The account. One row per person.

| Field | Type | Rules |
|---|---|---|
| `id` | uuid | primary key |
| `email` | text | **unique**, required |
| `displayName` | text | required |
| `settingPreferences` | text[] | multi-select from the Setting enum; at least one required |
| `categoryPreferences` | text[] | multi-select from the Category enum; at least one required |
| `difficultyPreference` | text | one of the Difficulty enum |
| `createdAt` | timestamptz | set on insert, never updated |

### QuestTemplate

The fixed curated library. **Never generated by AI** — these rows are authored by hand
and are the same for every user.

| Field | Type | Rules |
|---|---|---|
| `id` | uuid | primary key |
| `title` | text | required |
| `description` | text | required |
| `category` | text | one of the Category enum |
| `difficulty` | text | one of the Difficulty enum |
| `requiredSetting` | text | one of the Setting enum |

### DailyQuest

One row per quest assigned to a user. Created **on demand**, when the user taps
"Give me a quest" — there is no morning batch. `date` groups quests by day so streaks
can be calculated; the entity name reflects that grouping, not a daily generation cycle.

| Field | Type | Rules |
|---|---|---|
| `id` | uuid | primary key |
| `userId` | uuid | → User, required |
| `questTemplateId` | uuid | → QuestTemplate, required |
| `date` | date | the day this quest belongs to, required |
| `status` | text | one of `pending` · `completed` · `dismissed`; defaults to `pending` |
| `dismissedAt` | timestamptz | set only when status becomes `dismissed`; otherwise null |

### Item

An avatar item or spell. Fixed catalogue, same for everyone.

| Field | Type | Rules |
|---|---|---|
| `id` | uuid | primary key |
| `name` | text | required |
| `type` | text | e.g. robe, hat, staff, spell |
| `artAssetRef` | text | reference to the art asset — **pending reference images** (spec §10) |
| `unlockAtStreakWeeks` | integer | which weekly milestone unlocks it (1 = 7 days, 2 = 14 days…) |

### UserItem

Which items a user owns and which one is equipped.

| Field | Type | Rules |
|---|---|---|
| `id` | uuid | primary key |
| `userId` | uuid | → User, required |
| `itemId` | uuid | → Item, required |
| `owned` | boolean | default false |
| `equipped` | boolean | default false; **not exclusive** — several items may be equipped at once |

## Enums

Fixed value sets, taken verbatim from the spec. Nothing outside these lists is valid.

**Setting** — where a quest can be done:
`home` · `gym` · `outdoors` · `office/desk` · `school` · `park` · `mall`

**Category** — what kind of quest it is:
`fitness` · `mindfulness` · `productivity/chores` · `learning` · `fun activities` · `random activities`

**Status** — a DailyQuest's state:
`pending` · `completed` · `dismissed`

**Difficulty** — how hard a quest is:
`easy` · `medium` · `hard`

---

## Relationships

```
User ──< DailyQuest >── QuestTemplate
User ──< UserItem   >── Item
```

- A User has many DailyQuests; each DailyQuest points at exactly one QuestTemplate.
- A User has many UserItems; each UserItem points at exactly one Item.
- QuestTemplate and Item are shared catalogues owned by nobody.

---

## Rules the data model must enforce

These come from the spec and are not optional.

1. **Ownership.** Every DailyQuest and UserItem is readable and writable only by the
   user it belongs to — **enforced at the database or API layer, never only in the UI**
   (spec §5, and acceptance criterion 6).
2. **Eligibility.** A QuestTemplate is only assignable when its `requiredSetting` is in
   the user's `settingPreferences`, its `category` is in their `categoryPreferences`, and
   its `difficulty` matches their `difficultyPreference`.
3. **Library coverage.** The library must hold at least one quest for every
   setting x category x difficulty combination (7 x 6 x 3 = **126 minimum**), so no
   eligible combination can return empty. Guaranteed by content, not by runtime fallback.
4. **14-day dismissal cooldown.** Once dismissed, that template cannot be assigned to
   the same user again until 14 days after `dismissedAt`.
5. **Unique email** per User.
6. **No XP anywhere.** Unlocks are driven purely by `unlockAtStreakWeeks` against the
   user's streak (spec §3 notes).

---

## Derived, not stored

**Streak** is not a column. It is calculated from DailyQuest rows: consecutive days on
which the user has at least one `completed` quest, resetting to 0 after any full day
with none (spec §2 flow 2, acceptance criterion 7).

Storing it as a counter invites it drifting out of sync with the quests that justify it.
If the calculation ever becomes slow, cache it — but the DailyQuest rows stay the source
of truth.

## Open questions

Flagged rather than guessed, per the spec's own rule.

**Resolved:**

- Difficulty values: `easy` · `medium` · `hard`.
- Several items can be equipped at once — `equipped` is not exclusive.
- Empty-result risk is handled by library coverage (126 quests minimum), not by
  relaxing filters.
- Generation is on demand, one quest at a time.

**Still open:**

1. **`difficultyPreference` — single or multi?** Written as singular, unlike the two
   multi-select preference fields. Is it one chosen level, a maximum, or a mix? If it
   becomes multi-select, the 126-quest coverage floor still holds.
2. **One pending quest at a time?** Assumed yes: tapping "Give me a quest" while one is
   pending replaces it, and the replaced one is recorded as `dismissed` (and so enters
   the 14-day cooldown). Confirm this is wanted — it means rerolling burns templates.
3. **Art assets.** `artAssetRef` cannot be filled until reference images arrive.
4. **Platform.** Supabase or Base44 — undecided. Nothing above depends on it.
